Imagine sorting a pile of books by height. Instead of comparing every pair, you pick one book at random and make two piles: books shorter than it on the left, books taller on the right. That book is now exactly where it belongs, between the two piles. Then you do the same thing to each pile, and to each pile within those piles, until every pile has at most one book.

That's **quick sort**, and true to its name, it's one of the fastest general-purpose sorting algorithms in practice. Like [merge sort](/tutorials/algorithms/sorting/merge-sort), it uses divide and conquer, but it flips the strategy around. Merge sort does trivial splitting and careful combining. Quick sort does careful splitting (called **partitioning**) and needs no combining at all. It also sorts in place, without merge sort's extra array.

## The big idea

Quick sort works in three steps:

1. **Choose a pivot**: pick one element of the array.
2. **Partition**: rearrange the array so that every element smaller than the pivot comes before it, and every other element comes after it. The pivot lands in its **final sorted position**.
3. **Recurse**: quick sort the part to the left of the pivot and the part to the right of it.

The base case is a part with zero or one element, which is already sorted. Because the pivot ends up exactly where it belongs and each side only contains the right elements, there's nothing left to do once the recursion finishes: the whole array is sorted.

## Partitioning step by step

There are several ways to partition. We'll use the **Lomuto scheme**, which is the easiest to understand. It chooses the last element as the pivot and walks through the rest with an index `j`, while a second index `i` marks where the next small element should go. Whenever `arr[j]` is smaller than the pivot, it swaps that element into position `i` and moves `i` forward. At the end, it swaps the pivot into position `i`.

Let's partition `[7, 2, 1, 6, 8, 5, 3, 4]`:

```text
pivot = 4 (the last element), i = 0

j = 0   7 < 4? no                      [7, 2, 1, 6, 8, 5, 3, 4]
j = 1   2 < 4? yes → swap a[0], a[1]   [2, 7, 1, 6, 8, 5, 3, 4]   i = 1
j = 2   1 < 4? yes → swap a[1], a[2]   [2, 1, 7, 6, 8, 5, 3, 4]   i = 2
j = 3   6 < 4? no                      [2, 1, 7, 6, 8, 5, 3, 4]
j = 4   8 < 4? no                      [2, 1, 7, 6, 8, 5, 3, 4]
j = 5   5 < 4? no                      [2, 1, 7, 6, 8, 5, 3, 4]
j = 6   3 < 4? yes → swap a[2], a[6]   [2, 1, 3, 6, 8, 5, 7, 4]   i = 3
done    swap the pivot into a[3]       [2, 1, 3, 4, 8, 5, 7, 6]
```

After one pass, the array looks like this:

```text
[2, 1, 3]   4   [8, 5, 7, 6]
smaller   pivot   larger
```

The 4 is in its final position and will never move again. Neither side is sorted yet, but that's fine: quick sort now recursively sorts `[2, 1, 3]` and `[8, 5, 7, 6]` independently.

## Implementation

All three versions sort in place using Lomuto partitioning with the last element as the pivot. The highlighted lines are the divide-and-conquer core: partition, then recurse on each side.

<Tab>

```python title="quick_sort.py" {6-8}
def quick_sort(arr, lo=0, hi=None):
    """Sort arr in place in ascending order and return it."""
    if hi is None:
        hi = len(arr) - 1
    if lo < hi:
        p = partition(arr, lo, hi)
        quick_sort(arr, lo, p - 1)   # sort elements left of the pivot
        quick_sort(arr, p + 1, hi)   # sort elements right of the pivot
    return arr


def partition(arr, lo, hi):
    """Lomuto partition: place the pivot arr[hi] in its final position."""
    pivot = arr[hi]
    i = lo  # next slot for an element smaller than the pivot
    for j in range(lo, hi):
        if arr[j] < pivot:
            arr[i], arr[j] = arr[j], arr[i]
            i += 1
    arr[i], arr[hi] = arr[hi], arr[i]  # move the pivot between the parts
    return i


print(quick_sort([7, 2, 1, 6, 8, 5, 3, 4]))  # [1, 2, 3, 4, 5, 6, 7, 8]
```

function quickSort(arr, lo = 0, hi = arr.length - 1) {
  if (lo < hi) {
    const p = partition(arr, lo, hi);
    quickSort(arr, lo, p - 1); // sort elements left of the pivot
    quickSort(arr, p + 1, hi); // sort elements right of the pivot
  }
  return arr;
}

// Lomuto partition: place the pivot arr[hi] in its final position.
function partition(arr, lo, hi) {
  const pivot = arr[hi];
  let i = lo; // next slot for an element smaller than the pivot
  for (let j = lo; j < hi; j++) {
    if (arr[j] < pivot) {
      [arr[i], arr[j]] = [arr[j], arr[i]];
      i++;
    }
  }
  [arr[i], arr[hi]] = [arr[hi], arr[i]]; // move the pivot between the parts
  return i;
}

```java title="QuickSort.java" {10-12}
import java.util.Arrays;

public class QuickSort {
    public static void quickSort(int[] arr) {
        quickSort(arr, 0, arr.length - 1);
    }

    private static void quickSort(int[] arr, int lo, int hi) {
        if (lo < hi) {
            int p = partition(arr, lo, hi);
            quickSort(arr, lo, p - 1);  // sort elements left of the pivot
            quickSort(arr, p + 1, hi);  // sort elements right of the pivot
        }
    }

    // Lomuto partition: place the pivot arr[hi] in its final position.
    private static int partition(int[] arr, int lo, int hi) {
        int pivot = arr[hi];
        int i = lo; // next slot for an element smaller than the pivot
        for (int j = lo; j < hi; j++) {
            if (arr[j] < pivot) {
                swap(arr, i, j);
                i++;
            }
        }
        swap(arr, i, hi); // move the pivot between the parts
        return i;
    }

    private static void swap(int[] arr, int a, int b) {
        int temp = arr[a];
        arr[a] = arr[b];
        arr[b] = temp;
    }

    public static void main(String[] args) {
        int[] data = {7, 2, 1, 6, 8, 5, 3, 4};
        quickSort(data);
        System.out.println(Arrays.toString(data)); // [1, 2, 3, 4, 5, 6, 7, 8]
    }
}
```

<Callout type="note" title="The pivot is excluded from recursion">

Notice the recursive calls use `p - 1` and `p + 1`, skipping index `p`. The pivot is already in its final position, so it never needs to be examined again. Including it can cause infinite recursion when a partition makes no progress.

</Callout>

## Complexity analysis

| Case    | Time       | When it happens                                                   |
| ------- | ---------- | ----------------------------------------------------------------- |
| Best    | O(n log n) | Every pivot splits its range into two equal halves                |
| Average | O(n log n) | Random input, or random pivots on any input                       |
| Worst   | O(n²)      | Every pivot is the smallest or largest element in its range       |
| Space   | O(log n)   | Recursion stack on average; O(n) in the worst case                |

Each level of recursion does O(n) partitioning work in total. When pivots split ranges roughly in half, there are about log₂ n levels, giving O(n log n), just like merge sort. Even fairly lopsided splits, such as 90/10 every time, still give O(n log n) with a larger constant. On random input, quick sort makes about 1.39 n log₂ n comparisons on average.

### How the worst case happens

Now consider sorting an array that is **already sorted**, with the last element as the pivot. The pivot is always the largest value, so every partition puts all remaining elements on one side and nothing on the other:

```text
[1, 2, 3, 4, 5]   pivot 5 → [1, 2, 3, 4] and []
[1, 2, 3, 4]      pivot 4 → [1, 2, 3]    and []
[1, 2, 3]         pivot 3 → [1, 2]       and []
...
```

Each level removes just one element, so there are `n` levels doing `n`, `n − 1`, `n − 2`, ... comparisons: O(n²) in total. The recursion also goes `n` levels deep, which can cause a stack overflow on large inputs. The same thing happens with reverse-sorted input, and with arrays where every element is equal.

<Callout type="warning" title="Sorted input is not a rare edge case">

Real data is often already sorted or nearly sorted: timestamps, IDs, or a list someone sorted yesterday. A quick sort that always picks the first or last element as its pivot will hit its worst case on exactly this kind of everyday input.

</Callout>

## Choosing a pivot

The fix is to choose pivots more cleverly:

- **Random pivot**: pick a random index and swap that element to the end before partitioning. No particular input can reliably trigger the worst case, and the expected running time is O(n log n) on every input.
- **Median of three**: use the median of the first, middle, and last elements. It's cheap, deterministic, and handles sorted and reverse-sorted input well.

Adding a random pivot to our implementation takes just two lines at the start of `partition`:

```python title="random_pivot.py" {4-5}
import random

def partition(arr, lo, hi):
    r = random.randint(lo, hi)            # pick a random pivot index...
    arr[r], arr[hi] = arr[hi], arr[r]     # ...and move it to the end
    pivot = arr[hi]
    # ...the rest is unchanged
```

### Handling duplicates and deep recursion

Production implementations add a few more refinements:

- **Three-way partitioning** splits the range into elements less than, equal to, and greater than the pivot. Inputs with many repeated values then sort quickly instead of degrading to O(n²); an array of identical values takes just one pass.
- **Recursing into the smaller side first** and looping over the larger side caps the stack depth at O(log n), even in bad cases.
- **Introsort**, used by typical C++ `std::sort` implementations, watches the recursion depth and switches to heap sort (built on a [heap](/tutorials/data-structures/non-linear/heaps)) if it grows too large, guaranteeing O(n log n).

## Quick sort vs. merge sort

| Property     | Quick sort                       | Merge sort                          |
| ------------ | -------------------------------- | ----------------------------------- |
| Average time | O(n log n)                       | O(n log n)                          |
| Worst time   | O(n²), rare with good pivots     | O(n log n)                          |
| Extra space  | O(log n) for the stack           | O(n) for arrays                     |
| Stable       | No                               | Yes                                 |
| Best fit     | General-purpose in-memory arrays | Stable sorts, linked lists, huge data |

Quick sort is usually faster in practice for arrays: it works in place, its inner loop is tiny, and it scans memory sequentially, which keeps the CPU cache happy. That's why Java uses a dual-pivot quick sort for arrays of primitives. When stability or a hard worst-case guarantee matters, merge sort is the safer choice.

Quick sort is **not stable**: partitioning swaps elements across long distances, so equal elements can end up in a different relative order.

## Key takeaways

- Quick sort picks a pivot, partitions the array around it, and recursively sorts both sides.
- After partitioning, the pivot is in its final sorted position, so no combine step is needed.
- It averages O(n log n) time with only O(log n) extra space, and is often the fastest sort in practice.
- Its worst case is O(n²), triggered by consistently bad pivots, such as the last element of an already sorted array.
- Random or median-of-three pivots, three-way partitioning, and introsort make it robust in production.
