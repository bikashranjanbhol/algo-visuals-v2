You've lost your keys somewhere in the house. You have no idea where they are, so you check the kitchen counter, then the coat pockets, then the couch cushions, one place after another, until you find them. If they aren't anywhere, you only know that after you've checked *everywhere*.

That's **linear search** (also called *sequential search*): examine each item in order until you find the one you want or run out of items. It's the simplest search algorithm there is, it works on any collection, and it requires no preparation at all. It's also something you use constantly, often without realizing it, every time you call `in`, `indexOf`, or `contains`.

## How it works

Linear search takes a collection and a target value, and returns the position of the target, or a special value such as -1 if it isn't there.

1. Start at the first element.
2. Compare the current element with the target.
3. If they match, return the current position. You're done.
4. Otherwise, move to the next element and repeat from step 2.
5. If you reach the end without a match, report that the target was not found.

The algorithm makes no assumptions about the data. It doesn't need to be sorted, the values don't need to be numbers, and it works just as well on a [linked list](/tutorials/data-structures/linear/linked-lists) as on an [array](/tutorials/data-structures/linear/arrays).

### A worked example

Let's search `[8, 3, 5, 1, 9, 2]` for the value 1:

```text
index:  0  1  2  3  4  5
value:  8  3  5  1  9  2

check index 0:  8 ≠ 1
check index 1:  3 ≠ 1
check index 2:  5 ≠ 1
check index 3:  1 = 1  → found at index 3 after 4 comparisons
```

Now search the same array for 7. Every comparison fails, and only after checking all six elements can we return -1. An unsuccessful search is always the most expensive kind.

## Implementation

Each version returns the index of the **first** match, or -1 if the target is absent. The highlighted line is the early exit that makes successful searches stop as soon as possible.

<Tabs items={["Python", "JavaScript", "Java"]}>
<Tab>

```python title="linear_search.py" {5}
def linear_search(items, target):
    """Return the index of the first occurrence of target, or -1."""
    for i, item in enumerate(items):
        if item == target:
            return i  # found it, stop immediately
    return -1  # checked everything; it's not there


print(linear_search([8, 3, 5, 1, 9, 2], 1))  # 3
print(linear_search([8, 3, 5, 1, 9, 2], 7))  # -1
```

</Tab>

```javascript title="linearSearch.js" {4}
function linearSearch(items, target) {
  for (let i = 0; i < items.length; i++) {
    if (items[i] === target) {
      return i; // found it, stop immediately
    }
  }
  return -1; // checked everything; it's not there
}

console.log(linearSearch([8, 3, 5, 1, 9, 2], 1)); // 3
console.log(linearSearch([8, 3, 5, 1, 9, 2], 7)); // -1
```

```java title="LinearSearch.java" {5}
public class LinearSearch {
    public static int linearSearch(int[] items, int target) {
        for (int i = 0; i < items.length; i++) {
            if (items[i] == target) {
                return i; // found it, stop immediately
            }
        }
        return -1; // checked everything; it's not there
    }

    public static void main(String[] args) {
        int[] data = {8, 3, 5, 1, 9, 2};
        System.out.println(linearSearch(data, 1)); // 3
        System.out.println(linearSearch(data, 7)); // -1
    }
}
```

<Callout type="warning" title="Comparing objects in Java">

For primitives like `int`, `==` compares values. For objects such as `String`, `==` checks whether two references point to the *same object*, which is rarely what you want. When searching an array of objects, compare with `Objects.equals(items[i], target)` instead.

</Callout>

## Complexity analysis

| Case    | Time | When it happens                                    |
| ------- | ---- | -------------------------------------------------- |
| Best    | O(1) | The target is the first element                    |
| Average | O(n) | The target is somewhere in the middle              |
| Worst   | O(n) | The target is the last element, or not present     |
| Space   | O(1) | Only a loop index is needed                        |

If the target is present and equally likely to be at any position, linear search makes `(n + 1) / 2` comparisons on average. That's about half the list, but half of `n` is still proportional to `n`, so the average case is O(n). Double the list, and the expected search time doubles too.

Can we do better? Not without more information. If the data has no order, any element you skip could be the target, so every correct algorithm must, in the worst case, look at all `n` items. To beat O(n), you need structure, such as sorted data for [binary search](/tutorials/algorithms/searching/binary-search) or a [hash table](/tutorials/data-structures/non-linear/hash-tables).

## Variations

The basic pattern of walking through the items one by one adapts to many related tasks.

### Finding every match

To collect all matching positions, keep going instead of returning early:

```python title="find_all.py"
def find_all(items, target):
    return [i for i, item in enumerate(items) if item == target]


print(find_all([4, 7, 4, 1, 4], 4))  # [0, 2, 4]
```

This always takes O(n), since it must examine every element to be sure it found them all.

### Searching by a condition

Often you aren't looking for an exact value, but for the first item that satisfies some condition, such as the first negative number or the first user who is offline. That's still linear search, just with a different test. Most languages provide it built in:

<Tabs items={["Python", "JavaScript", "Java"]}>
<Tab>

```python title="builtins.py"
nums = [8, 3, -5, 1, -9]

print(3 in nums)          # True: linear search under the hood
print(nums.index(1))      # 3 (raises ValueError if missing)

first_negative = next((x for x in nums if x < 0), None)
print(first_negative)     # -5
```

</Tab>
<Tab>

```javascript title="builtins.js"
const nums = [8, 3, -5, 1, -9];

console.log(nums.includes(3)); // true: linear search under the hood
console.log(nums.indexOf(1)); // 3 (or -1 if missing)

const firstNegative = nums.find((x) => x < 0);
console.log(firstNegative); // -5 (or undefined if none)
```

</Tab>
<Tab>

```java title="Builtins.java"
import java.util.Arrays;
import java.util.List;
import java.util.OptionalInt;

public class Builtins {
    public static void main(String[] args) {
        List<Integer> nums = List.of(8, 3, -5, 1, -9);

        System.out.println(nums.contains(3)); // true: linear search under the hood
        System.out.println(nums.indexOf(1));  // 3 (or -1 if missing)

        OptionalInt firstNegative = Arrays.stream(new int[] {8, 3, -5, 1, -9})
                .filter(x -> x < 0)
                .findFirst();
        System.out.println(firstNegative.getAsInt()); // -5
    }
}
```

</Tab>
</Tabs>

<Callout type="tip" title="Hidden linear searches add up">

Because `in`, `includes`, and `contains` scan the whole list, calling them inside a loop quietly creates an O(n²) algorithm. If you need to check membership many times, put the items in a set first. A set is backed by a [hash table](/tutorials/data-structures/non-linear/hash-tables), so each lookup takes O(1) time on average.

</Callout>

## When to use it

Linear search is the right tool more often than you might think:

- **The data is unsorted** and you only need to search it once or a few times.
- **The collection is small.** For a few dozen items, a simple scan is often faster than anything fancier, thanks to its low overhead.
- **You only have sequential access**, as with a linked list or a stream of data arriving over a network.
- **You're matching a complex condition** that no index or sort order can help with.

### Linear search vs. sorting first

If you will search the same data many times, it can pay to sort it once and then use binary search. Sorting costs O(n log n), after which each search costs only O(log n). Doing `k` linear searches costs O(k × n) in total. Roughly speaking, once you plan to search more than about log₂ n times, sorting first starts to win. For a million items, that break-even point is only around 20 searches.

| Approach           | Preparation             | Cost per search | Extra space |
| ------------------ | ----------------------- | --------------- | ----------- |
| Linear search      | None                    | O(n)            | O(1)        |
| Binary search      | Sort once: O(n log n)   | O(log n)        | O(1)        |
| Hash set lookup    | Build the set: O(n)     | O(1) on average | O(n)        |

## Key takeaways

- Linear search checks each element in order until it finds the target or reaches the end.
- It works on any collection, sorted or not, and needs no preparation or extra memory.
- It takes O(1) time in the best case and O(n) in the average and worst cases.
- Built-in helpers like `in`, `indexOf`, and `contains` are linear searches, so avoid calling them in loops over large data.
- For repeated searches, sorting plus binary search, or a hash set, is usually much faster.
