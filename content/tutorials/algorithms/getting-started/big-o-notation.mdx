How do you compare two algorithms? You could time them, but the result depends on your laptop, your programming language, what else is running, and the particular input you picked. Computer scientists needed a way to talk about speed that ignores all of that noise and captures the essential question: **as the input gets bigger, how much more work does the algorithm do?**

Big-O notation is that language. It's the single most important tool for reasoning about algorithms, and you'll see it everywhere: in library documentation, in technical interviews, and in every other topic of this tutorial. By the end of this page you'll be able to look at a piece of code and estimate its complexity yourself.

## Counting steps, not seconds

Instead of measuring time, we count **basic operations**: comparisons, arithmetic, assignments, and reading or writing an array element. Each of these takes roughly constant time on any machine. Then we express the count as a function of the input size, `n`.

Consider summing a list:

```python title="total.py"
def total(numbers):
    result = 0           # 1 step
    for x in numbers:    # the loop body runs n times
        result += x      # 1 step per iteration
    return result        # 1 step
```

That's roughly `n + 2` steps. If the list has a million elements, the `+ 2` is irrelevant. What matters is that the work grows **in proportion to** `n`. That proportionality is exactly what Big-O captures: this function is O(n).

## The rules of Big-O

Big-O describes the **growth rate** of a function, focusing on what happens as `n` becomes very large. Two simplification rules get you most of the way.

### Drop constant factors

An algorithm that does `3n` steps and one that does `n` steps are both O(n). Constant factors depend on hardware, language, and implementation details, and they don't change the *shape* of the growth: double the input, and both algorithms do double the work.

### Keep the dominant term

If an algorithm does `n² + 100n + 5000` steps, then for large `n` the `n²` term dwarfs everything else. At `n = 10,000`, the `n²` term is 100,000,000 while `100n` is only 1,000,000. So the whole expression is simply O(n²).

### The formal definition

Formally, `f(n)` is O(g(n)) if there exist positive constants `c` and `n₀` such that `f(n) ≤ c · g(n)` for every `n ≥ n₀`. In plain English: beyond some point, `f` never grows faster than a constant multiple of `g`. That's why Big-O is described as an **upper bound** on growth.

## Common complexity classes

A handful of growth rates show up again and again. From fastest to slowest:

| Big-O      | Name         | Typical example                                                      |
| ---------- | ------------ | -------------------------------------------------------------------- |
| O(1)       | Constant     | Reading `arr[i]`, pushing onto a [stack](/tutorials/data-structures/linear/stacks) |
| O(log n)   | Logarithmic  | [Binary search](/tutorials/algorithms/searching/binary-search)        |
| O(n)       | Linear       | [Linear search](/tutorials/algorithms/searching/linear-search), finding the maximum |
| O(n log n) | Linearithmic | [Merge sort](/tutorials/algorithms/sorting/merge-sort), [quick sort](/tutorials/algorithms/sorting/quick-sort) on average |
| O(n²)      | Quadratic    | [Bubble sort](/tutorials/algorithms/sorting/bubble-sort), comparing every pair |
| O(2ⁿ)      | Exponential  | Naive recursive Fibonacci, listing every subset                      |
| O(n!)      | Factorial    | Trying every possible ordering of `n` items                          |

The differences look abstract until you plug in numbers. Here is roughly how many steps each class needs:

| n         | log₂ n | n log₂ n       | n²        | 2ⁿ           |
| --------- | ------ | -------------- | --------- | ------------ |
| 10        | 3      | 33             | 100       | 1,024        |
| 100       | 7      | 664            | 10,000    | 1.3 × 10³⁰   |
| 1,000     | 10     | 9,966          | 1,000,000 | 1.1 × 10³⁰¹  |
| 1,000,000 | 20     | 19.9 million   | 10¹²      | unimaginable |

<Callout type="tip" title="Why this matters in real life">

At a billion simple operations per second, an O(n²) algorithm on a million items needs about 10¹² operations: roughly 17 minutes. An O(n log n) algorithm on the same input needs about 20 million operations, which takes a fiftieth of a second. No hardware upgrade can close a gap like that; only a better algorithm can.

</Callout>

### Seeing the classes in code

Each function below is a small, recognizable pattern. Learning to spot these shapes is most of what complexity analysis is in practice.

```python title="complexity.py" {15-16}
# O(1): the same work no matter how long the list is
def first(items):
    return items[0]

# O(n): touches each element at most once
def contains(items, target):
    for item in items:
        if item == target:
            return True
    return False

# O(n²): a loop inside a loop over the same data
def has_duplicate(items):
    n = len(items)
    for i in range(n):
        for j in range(i + 1, n):
            if items[i] == items[j]:
                return True
    return False

# O(log n): the remaining work halves every iteration
def count_halvings(n):
    steps = 0
    while n > 1:
        n //= 2
        steps += 1
    return steps
```

  while (n > 1) {
    n = Math.floor(n / 2);

  }

            if (item == target) return true;
        }
        return false;
    }

    static boolean hasDuplicate(int[] items) {
        int n = items.length;
        for (int i = 0; i < n; i++) {
            for (int j = i + 1; j < n; j++) {
                if (items[i] == items[j]) return true;
            }
        }
        return false;
    }

    // O(log n): the remaining work halves every iteration
    static int countHalvings(int n) {
        int steps = 0;
        while (n > 1) {
            n /= 2;
            steps++;
        }
        return steps;
    }
}

In `has_duplicate`, the inner loop runs `n − 1` times, then `n − 2`, and so on down to 0. That adds up to `n(n − 1) / 2` comparisons, which is about half of `n²`. Drop the constant ½ and the lower-order term, and you get O(n²).

## Analyzing code

You can estimate the complexity of most code with a few rules of thumb.

### Sequential steps add

Two loops one after the other cost O(n) + O(n) = O(2n), which is just O(n). If one part is O(n) and another is O(n²), the total is O(n²): the slower part dominates.

### Nested loops multiply

A loop of `n` iterations inside another loop of `n` iterations does `n × n` work: O(n²). Be careful when the loops run over *different* inputs. A loop over `a` items nested inside a loop over `b` items is O(a × b), not O(n²).

### Halving means logarithms

If each step cuts the remaining problem in half, the number of steps is the number of times you can halve `n` before reaching 1, which is log₂ n. That's why [binary search](/tutorials/algorithms/searching/binary-search) is so fast. In Big-O we usually just write O(log n), since logarithms in different bases differ only by a constant factor.

<Callout type="warning" title="Watch for hidden loops">

A single line of code is not always O(1). In Python, `x in my_list`, `my_list.index(x)`, `my_list.insert(0, x)`, and slicing all take linear time. In JavaScript, the same is true of `includes`, `indexOf`, and `shift`. Calling one of these inside a loop quietly turns an O(n) algorithm into O(n²).

</Callout>

## Best, average, and worst case

The same algorithm can do very different amounts of work depending on the input. [Linear search](/tutorials/algorithms/searching/linear-search) finds its target in one step if it happens to be first (the **best case**), but must check all `n` items if the target is missing (the **worst case**).

We usually quote the worst case, because it's a guarantee: no input can make the algorithm slower than that. Sometimes the average case is what matters in practice. [Quick sort](/tutorials/algorithms/sorting/quick-sort) is the famous example: O(n log n) on average, but O(n²) in its worst case.

### Big-O, Big-Ω, and Big-Θ

Big-O has two siblings:

- **Big-O** is an upper bound: the function grows *no faster* than this.
- **Big-Ω** (omega) is a lower bound: the function grows *at least* this fast.
- **Big-Θ** (theta) is a tight bound: both at once.

<Callout type="note">

In everyday conversation, people say "Big-O" when they really mean the tight bound. Saying merge sort is O(n³) is technically true, because it grows no faster than n³, but it's useless. Always give the tightest bound you can.

</Callout>

## Space complexity

Big-O also describes memory. **Space complexity** measures the extra memory an algorithm needs beyond its input, often called *auxiliary space*. Finding the maximum of a list uses O(1) extra space: one variable, no matter how long the list. [Merge sort](/tutorials/algorithms/sorting/merge-sort) uses O(n) extra space for its temporary arrays. And [recursive functions](/tutorials/algorithms/getting-started/recursion) use stack space proportional to their maximum recursion depth, which is easy to overlook.

Time and space often trade off against each other. Storing results in a [hash table](/tutorials/data-structures/non-linear/hash-tables) can turn a slow algorithm into a fast one at the cost of extra memory, an idea you'll meet again in [dynamic programming](/tutorials/dynamic-programming).

## Key takeaways

- Big-O describes how an algorithm's work grows as the input size `n` grows, independent of hardware.
- Drop constant factors and keep only the dominant term: `3n² + 5n + 2` is O(n²).
- The common classes, from fastest to slowest: O(1), O(log n), O(n), O(n log n), O(n²), O(2ⁿ), O(n!).
- Sequential code adds, nested loops multiply, and repeated halving gives a logarithm.
- Specify which case you mean (best, average, or worst), and remember that space complexity matters too.
