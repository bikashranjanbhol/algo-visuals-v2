**TF9.** Returning an accepted-job identity proves eventual success.  
**TF10.** The same product can combine synchronous requests and asynchronous notifications.

### Answer key: read after completing all questions

#### Multiple-choice answers

| Question | Answer | Explanation |
|---|---|---|
| MC1 | B | Characterization describes the problem before implementation choices |
| MC2 | A | Explicit exceptions make the target flexible; importance is independent |
| MC3 | C | Cancellation is behavior; the other statements concern quality or constraints |
| MC4 | D | Feature scope and performance negotiability are different axes |
| MC5 | B | Divide 900 and 100 by 100: 9 reads for each write |
| MC6 | C | Deletion changes stored profile data |
| MC7 | A | Required cart state can live outside individual app servers |
| MC8 | D | Recoverable shared state can survive a specified server failure; routing alone cannot |
| MC9 | B | Grouped monthly calculation proceeds before final results are returned |
| MC10 | C | Frequent small groups are micro-batches |
| MC11 | A | Active event evaluation is online even without a waiting person |
| MC12 | D | Offline describes deferred operational timing here, not absence of networking |
| MC13 | B | Queued work is accepted; file preparation still has an outcome to discover |
| MC14 | C | Timeout only establishes that the caller stopped waiting without confirmation |
| MC15 | A | Identity does not prove submitted values satisfy rules |
| MC16 | D | Organizational customers establish B2B; device activity determines load |
| MC17 | B | Authorization checks the specific requested permission |
| MC18 | C | Geography of users does not dictate number of deployment regions |
| MC19 | A | Sharing at the application boundary coexists with dedicated databases |
| MC20 | D | One tenant consumes capacity that other tenants need |

#### True/false explanations

1. **True.** Encryption can be a quality constraint, an acceptance condition, and required for release.
2. **False.** Stateless application handling can consult persistent shared data.
3. **False.** Waiting work grows whenever arrivals exceed processing for a sustained period.
4. **True.** Computing and viewing a report are different operations.
5. **True.** Identity proof does not make a client-controlled price authoritative.
6. **False.** A global service may keep authoritative writes in selected locations.
7. **True.** Monthly payroll can require completion before payday.
8. **False.** B2B products may use shared, dedicated, or hybrid deployments.
9. **False.** Acceptance must be followed by a reported success or failure; retries may not succeed.
10. **True.** These are independent workflow choices within one product.

#### Short-answer models

1. Describe important properties of the problem and its work so the design matches actual needs.
2. A constraint limits acceptable solutions; an assumption is an unconfirmed belief used provisionally. Validate assumptions and identify consequences if false.
3. Latency is one person's order-to-coffee wait. Throughput is coffees completed per minute. High throughput does not guarantee short individual waits.
4. A shop must offer search, while a normally sub-500-ms search target permits occasional agreed delay. Search remains in scope despite a missed target.
5. Local session independence says nothing about removing cart, account, or order records from shared storage.
6. An arriving sensor reading can trigger online alarm evaluation without a human interacting and awaiting the result. Interactive additionally describes active caller participation.
7. At minimum, accepted/queued, running, complete with access to the result, and failed with an understandable next step. Define expiry or cancellation when relevant.
8. Authentication establishes identity; authorization checks permission for an action on a resource. A valid identity can lack document access.
9. Where may data be stored and processed? What latency is needed in each area? What recovery geography is allowed? Other valid answers include time zones and local language needs.
10. Shared app/data store lowers per-tenant resource cost but requires pervasive tenant checks. Dedicated deployment improves resource separation but increases environments and operating cost. Shared app/separate databases is another valid model.

#### Scenario solutions

1. Ratio = 10,000,000:100,000 = **100:1**, read-heavy by logical count. Ask how stale a product price or description may be and which reads must be authoritative. Read cost and images still need measurement.
2. Local session dependence was hidden by normal routing. Sticky routing can preserve ordinary placement but fails if A dies; shared recoverable sessions can serve B but add capacity and recovery obligations. Validated request-carried proof is another possibility with expiry and revocation considerations.
3. Synchronous acceptance, asynchronous preparation. Display queued, processing, ready, and failed, with a way to obtain final status. Readiness latency is two minutes, not the acknowledgment time.
4. The browser remains untrusted despite being used by an employee. Authenticate, authorize the purchase, calculate the applicable server-side price, and check quantities and discounts. A submitted ₹1 total is not the pricing rule.
5. Distance to the required data location creates a lower bound on remote round trips. Clarify covered data, targets, and permitted processing; nearby public or permitted content may help. If targets remain contradictory, stakeholders must relax or rescope a demand.
6. B2B market and external customer access, with single-tenant application deployments. Payroll calculation is batch/offline and often asynchronously submitted; viewing results is interactive/online. Persistent records remain stateful even with replaceable workers. Customer browser trust still requires checks.
7. Identify the caller, establish authorized tenant membership and active scope, verify report ownership or explicit sharing, and check the requested permission. Existence of an identifier is not access permission.
8. 2,000 × 4 = **8,000 readings/s**. Missing facts include reading size, synchronized peaks, reads, retention, per-reading processing, and required completion delay. Average alone cannot size capacity.
9. A fresh operation identity can trigger a second charge. Resolve the original result or retry using the same agreed identity with duplicate-effect protection. A timeout did not undo successful work.
10. Browsing: read-heavy interactive online synchronous, suggesting efficient fresh-enough reads. Ordering: online interactive writes with synchronous acceptance, requiring validated durable records and duplicate handling. Notifications: async, requiring final delivery/failure tracking. Analytics: offline batch, requiring scheduled capacity and safe reruns. Each need admits multiple implementations.

Use incorrect answers to choose sections to revisit. A strong answer names assumptions and consequences. Memorizing a label without defining its scope is insufficient.

## 99. Forty-eight flashcards

Cover the answer and recall it aloud before checking.

**Q1: What is a software system?**  
**A:** Cooperating software, computers, and information that accomplish a purpose.

**Q2: What is a requirement?**  
**A:** A capability, quality, or condition an acceptable solution must satisfy.

**Q3: What is requirement characterization?**  
**A:** Describing problem and workload properties to guide design.

**Q4: Why characterize before architecture?**  
**A:** Different needs require different arrangements and trade-offs.

**Q5: What is a hard requirement?**  
**A:** A condition that cannot be relaxed within the agreed acceptance scope.

**Q6: What is a soft requirement?**  
**A:** A target permitting specified acceptable deviations.

**Q7: Does soft mean optional?**  
**A:** No. A flexible target can still be important and in scope.

**Q8: What is a functional requirement?**  
**A:** A statement of behavior the system must provide.

**Q9: What is a non-functional requirement?**  
**A:** A quality or constraint under which behavior must operate.

**Q10: What is must-have?**  
**A:** Essential to the purpose or agreed scope of this product version.

**Q11: What is nice-to-have?**  
**A:** Valuable but postponable without defeating that version's purpose.

**Q12: Is must-have the same as hard?**  
**A:** No. Scope and negotiability are different questions.

**Q13: What is MVP?**  
**A:** Minimum Viable Product: the smallest useful, acceptable product scope.

**Q14: What is a read?**  
**A:** Retrieving existing data.

**Q15: What is a write?**  
**A:** Creating, changing, or deleting data.

**Q16: What does read-heavy mean?**  
**A:** Reads dominate the stated measurement at a defined boundary.

**Q17: What does write-heavy mean?**  
**A:** Writes dominate the stated measurement at a defined boundary.

**Q18: What is a read/write ratio?**  
**A:** A comparison of read and write quantities over the same scope and period.

**Q19: Can one product contain both workload types?**  
**A:** Yes; browsing and ingestion may have different patterns.

**Q20: What is state?**  
**A:** Remembered information about prior work or current condition that affects behavior.

**Q21: What is locally stateful handling?**  
**A:** Handling that depends on information privately remembered by a particular server.

**Q22: What is stateless application handling?**  
**A:** Requests do not require that app server's private history from earlier requests.

**Q23: Can a stateless app use a database?**  
**A:** Yes. Persistent state can live in shared storage.

**Q24: What is a sticky session?**  
**A:** Routing related requests to the same server.

**Q25: What is interactive processing?**  
**A:** Processing for an active caller waiting for a useful result.

**Q26: What is batch processing?**  
**A:** Processing a collection of work as a group.

**Q27: What is micro-batching?**  
**A:** Processing frequent small groups, with grouping delay.

**Q28: What is online processing here?**  
**A:** Work on the active operational path with results needed reasonably soon.

**Q29: What is offline processing here?**  
**A:** Deferred work outside the immediate operational request path.

**Q30: What is synchronous completion?**  
**A:** The dependent caller waits for the operation's result.

**Q31: What is asynchronous completion?**  
**A:** Acceptance and final outcome occur separately; the caller can continue.

**Q32: Does accepted mean completed?**  
**A:** No; final work can still be running or fail.

**Q33: What is an internal system?**  
**A:** A system mainly used within an organization.

**Q34: What is an external system?**  
**A:** A system serving customers, partners, or the public.

**Q35: What is B2B?**  
**A:** Business-to-business: serving organizations as customers.

**Q36: What is B2C?**  
**A:** Business-to-consumer: serving individual consumers.

**Q37: What is a trusted client?**  
**A:** A client with stronger justified control and identity assurances for specified actions.

**Q38: What is an untrusted client?**  
**A:** A client whose behavior or claims are not reliably controlled by the service.

**Q39: What is a trust boundary?**  
**A:** A crossing between areas with different trust or control assumptions.

**Q40: What is authentication?**  
**A:** Checking identity.

**Q41: What is authorization?**  
**A:** Checking permission for a particular action or resource.

**Q42: What is a regional system?**  
**A:** One primarily serving a defined geographic scope.

**Q43: What is a global system?**  
**A:** One serving users across widely separated geographic areas.

**Q44: Does global mean multi-region deployment?**  
**A:** No. Audience geography and infrastructure placement differ.

**Q45: What is a tenant?**  
**A:** A customer boundary for data, configuration, and access, often an organization.

**Q46: What are single-tenancy and multi-tenancy?**  
**A:** Serving one versus several tenant boundaries at a specified deployment or resource scope.

**Q47: What is tenant isolation?**  
**A:** Preventing improper access and interference across customer boundaries.

**Q48: What is a noisy neighbor?**  
**A:** A tenant whose resource use degrades service for others sharing capacity.

## 100. Summary cheat sheet

| Characterization | Core question | Possible implication | Useful clarification | Frequent mistake |
|---|---|---|---|---|
| Hard / soft | What deviations are acceptable? | Strong checks or negotiated exceptions | What happens if missed? | Soft means unimportant |
| Functional / non-functional | What, how well, or under what conditions? | Behaviors plus measured quality | How do we verify it? | Arguing labels instead of clarity |
| Must / nice | Is this version viable without it? | Scope control | What is needed at launch? | Must-have equals absolute guarantee |
| Read / write-heavy | Which operations dominate? | Read copies or write capacity | Counts, cost, bytes, peaks? | Read-heavy means no writes |
| Stateful / stateless | Where does required history live? | Placement or shared access | Must the same server handle the next request? | Stateless means no database |
| Interactive / batch | Who waits, and are items grouped? | Delay or grouped efficiency | Immediate result or deadline? | All product workflows match |
| Online / offline | Active operation or deferred work? | Live path or prepared results | How fresh must it be? | Offline means no internet |
| Sync / async | Wait for final result or accept now? | Direct answer or job tracking | How are failures and duplicates exposed? | Accepted means successful |
| Internal / external | Who accesses this part? | Identity and exposure policies | Users versus dependencies? | Internal means secure by default |
| B2B / B2C | Who buys, uses, and administers? | Organization or consumer workflows | Users/devices per customer? | B2B means low scale |
| Trusted / untrusted | Which caller claims can be justified? | Server-enforced checks | Who controls the device? | Sign-in makes all input trustworthy |
| Regional / global | Where are users and obligations? | Selected proximity and recovery | Where may data live? | Global means writes everywhere |
| Single / multi-tenant | Which customer boundaries share resources? | Isolation and fair-use controls | App, store, or deployment shared? | Multi-tenant requires one table set |

Always state the scope, evidence, and assumptions behind a label. A useful one-paragraph characterization can be:

> The launch food-delivery browsing path is read-heavy, interactive, online, and synchronous; menu-copy freshness needs agreement. Order acceptance writes durable records and starts a persistent workflow with hard ownership, price, and duplicate-effect rules. Notifications can finish asynchronously; daily analytics is offline batch work. The platform serves consumers and restaurant organizations through untrusted external clients, with protected internal administration. It starts regionally. Restaurant administration shares application resources across tenant boundaries; private orders require participant-specific permissions. These findings motivate efficient reads, authoritative order handling, job outcomes, and tenant-aware access before technology selection.

## 101. Final mental model

Before designing a system, ask:

| Ask | Dimension it reveals |
|---|---|
| WHAT must it do? | Functional requirements |
| HOW WELL must it work, and under what constraints? | Non-functional requirements |
| WHICH conditions cannot be compromised? | Hard versus soft |
| WHAT is essential to this product version? | Must-have versus nice-to-have |
| WHAT does the workload look like? | Read-heavy versus write-heavy |
| WHERE does required state live? | Stateful versus stateless at each layer |
| IS someone waiting, and is work grouped? | Interactive versus batch |
| WHEN must work happen? | Online versus offline |
| DOES the caller wait for final completion? | Synchronous versus asynchronous |
| WHO accesses the system? | Internal versus external |
| WHO buys and uses it? | B2B versus B2C and other models |
| HOW MUCH can we trust each caller claim? | Trusted versus untrusted clients |
| WHERE are users, computation, and permitted data? | Regional versus global |
| HOW MANY customer boundaries share which resources? | Single-tenant versus multi-tenant |

Problem → requirement → characterization → architectural implication → technology choice. Revisit assumptions when evidence changes.

## 102. Recommended learning progression

A **back-of-the-envelope estimate** is a rough calculation used to test plausibility, like estimating meals needed from guest count; workload rates and storage estimates are software examples. It matters because even approximate numbers can rule out unsuitable designs.

| Next topic | Why it follows |
|---|---|
| Functional requirements | Make user actions and outcomes explicit |
| Non-functional requirements | Turn quality goals into checkable conditions |
| Requirement characterization | Combine requirements into a coherent problem picture |
| Back-of-the-envelope estimation | Put approximate quantities behind that picture |
| Read/write workloads | Understand which operations consume capacity |
| Stateful/stateless architecture | Decide where remembered information belongs |
| Synchronous/asynchronous systems | Decide when results and failures become visible |
| APIs | Specify agreements between callers and services |
| Networking | Understand message travel, delay, and partial failure |
| Databases | Organize persistent records and controlled updates |
| Caching | Safely reuse data while meeting freshness needs |
| Queues and messaging | Coordinate delayed work and burst handling |
| Scalability | Grow capacity while preserving the promised behavior |
| Distributed systems | Reason about coordination among independently failing computers |

These topics overlap. Return to earlier concepts as later examples make them concrete. Study implementation tools only after you can explain which requirement would justify them.

### Primary-source notes and optional further reading

The teaching scenarios and calculations are authored examples. The links below support three narrower technical distinctions; they are optional reading, not prerequisites.

- [IETF RFC 9110, HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html): HTTP is specified as a stateless request/response protocol. That protocol description does not establish whether application servers keep session state; Section 21 distinguishes the scopes.
- [AWS, SaaS tenant isolation strategies](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/core-isolation-concepts.html): isolation concerns tenant-resource access and spans different architectural models. Sections 53–54 use resource-specific sharing boundaries rather than equating SaaS with one shared database.
- [PostgreSQL documentation, introduction to indexes](https://www.postgresql.org/docs/17/indexes-intro.html): indexes can accelerate retrieval while adding storage and data-change overhead. Section 15 introduces the trade-off without assuming every workload needs more indexes.

You are ready to move from characterization to architecture when you can explain the workload, constraints, uncertainty, and consequences in plain language—and justify a proposed component from those needs.
